# Experience matrix (P-01)

Status: S1 preview, issue #40. Generated from the source catalogs on `main` at `7d4a696` (`src/engine/items.ts`, `src/engine/beats.ts`, `src/engine/places.ts`, `character-kit/runtime/animations/manifest.json`, `worker/core/mcp-tools.ts`). Row schema follows contract C02.

I-06 update (#53, 2026-11-02, `feature/i06-item-effects`): the 58 item rows in section 3 are regenerated from `ITEM_EFFECTS` in `src/engine/items.ts`. Earlier rows marked every item `rule / complete`; that overstated the build. Now each row names the implemented effect rule or says `effect none (fallback)` with the reason, the visual status is `fallback` unless the item is a modelled prop, and items with no source and no rule are `planned`. `scripts/items.test.mjs` (`AC1 coverage`) fails if a row's effect or trade column disagrees with the source (`ITEM_EFFECTS`, `checkTrade`).

How to read this file:
- **sourceMode** records each feature's source as of the catalog snapshot at `7d4a696` and the later P-02–P-04 row updates; it does not prove that the whole experience passed S2/S3 acceptance: `live` (real call or real verification), `rule` (engine rule), `scripted` (the 3:30 story), `replay` (recorded output), `planned` (not built yet; shown only as guidance, never emitted as a live event).
- **visualStatus**: `complete`, `fallback` (a substitute clip or icon is shown and labelled), `missing`.
- **ownerTask**: the S1 task that fixes the preview experience, then the S2 task that implements it. After P-07 passes, S2 and S3 continue without a planned stop; each stage keeps its own acceptance evidence. S3 verification tasks are listed in section 9.
- The preview never promotes fixture state to a real claim, delegation or reward (C02).

`postcard:<placeId>` is generated for every named place in section 5; it is one ItemSpec (`postcard`) with provenance. Its effect is none (fallback): mailing it is the Postage Stamp rule.

How the item rules work (I-06):
- **Effect**: an item changes abilities only through one of the nine rules in `EFFECT_RULES` (`bus_speed`, `teleport`, `plant`, `bloom_seed`, `send_postcard`, `night_sky`, `extra_activity`, `extra_spotlight`, `campfire_invite`). Every other id has `effect: 'none'` with a reason. `abilityGain` (the "no ability change, no trade" rule) follows the same table, with two additions: an item in the receiver's public `wants` counts (Sunny takes an Invite Token, Tempo an Event Pass), and Clover Seed, Fruit, Coffee, Tea, Wildflower, every crafted item and postcards count as goal items. So Pastry, Snack Box, Spark and Event Pass trade only to a receiver that wants them (or when the other side gains). `ItemSpec.ability` is set only where a rule implements it.
- **Spotlight Ticket**: spent at the end of a tick, after that tick's turn; the holder's extra turn is the next tick. The heartbeat picks the spotlight from the committed state before the tick, so its model call is for the Muse that really gets the turn. A paused or connected Muse keeps its ticket.
- **Finds**: a Muse holding a pass does not find a second one of the same pass; the find draws another item from the place.
- **Expiry**: an item with `expiresHours` (the four passes) is valid from its acquisition until acquisition + 24 h; at exactly 24 h it is expired. The clock starts only when the item first comes into the world (find, craft, reward). A trade, gift or postcard hands the remaining time on: a pass held 20 h by one Muse expires 4 h after another receives it, so passing it around never renews it. Mail carries the clock in transit. The tick, every MCP write and following the owner run the sweep first, and `checkTrade` refuses an expired copy (`expired`) even before a sweep. An expired copy leaves the inventory with an `item_expired` event and an `expired` history entry. A copy in a state stored before I-06 starts its clock at the first sweep.
- **History**: `appendHistory` is the only writer. Each entry has `seq`, `prevHash` and `hash` (SHA-256 over the JCS form of the entry without `hash`). The state keeps the newest 200; `chain.anchor` is the hash of the last entry trimmed away, so the oldest kept entry still links. `verifyHistory` rejects edited, deleted, reordered or inserted entries, and writes refuse to extend a tampered tail (`HistoryTamperError`). Entries stored before the chain have no hash and count as legacy, before genesis. Start items and the welcome gift are not moves, so they leave no entry.
- **Tampered history**: every tick and every item write checks the tail; the day change verifies every kept entry. On a fault the ledger keeps `tamper` (sticky until someone repairs the history), the tick logs `history_tamper` once a day and skips the item rules (upkeep, finds, trades, crafts, Spotlight Tickets), and movement, beats, greetings and the spotlight go on. MCP item writes are refused with `history_tamper`; other writes still run.
