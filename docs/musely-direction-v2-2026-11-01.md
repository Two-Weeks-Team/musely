# Musely 방향 확정 v2 — 신원·위임과 프리뷰 데모 (2026-11-01)

상태: 방향 확정안. 이 문서가 병합되면 데모 단계의 기준이 된다.
수용 대상: #7 (신원·위임 설계 초안 v1과 후속 댓글, 장상근), #8 (프리뷰 데모 v2 설계), #9 (보상 + A2A 자율 상호작용 루프, 장상근), #12 (커스텀 커넥터/MCP 입장·비용 모델, 장상근), 11/1 통화 회의록 `meetings/2026-11-01-sync-call.md`
진행: 김세준 주도로 합의(11/1). 장상근은 신원·위임과 보상 기반 A2A 조사를 맡는다.

## 1. 의도와 목적

**2단계로 진행한다.**
1. **지금**: preview.musely.net을 완전한 데모로 만든다. 구현이 가능하다는 것을 증명하고, 심사 기준에서 수상 가능성을 최대로 높인다.
2. **그다음**: 실제 구현(서버·에이전트·인증·모델 연동)을 하고 GTM으로 간다. 데모의 구조는 이 구현과 1:1로 대응하도록 설계한다.

**데모가 증명할 두 축** (11/1 통화 결정)
1. **신원·위임**: 이 Muse가 누구에게 위임받았고 무엇을 할 수 있는지 서로 확인한 뒤에만 함께 행동한다.
2. **보상(아이템)**: 에이전트가 실제 장소에서 아이템을 얻으면 능력이 바뀐다. 에이전트끼리 아이템을 주고받는다. 사람은 이 과정을 지켜본다. 보상은 사용자가 계속 개입하지 않아도 에이전트가 스스로 움직이는 이유다.

**범위를 최대로 잡는 이유**
- 임팩트 있는 장면을 미리 예측해서 만들려는 것이 아니다. 실제로 움직이는 세계를 만들고, 그 움직임 속에서 나온 장면을 골라 3분 영상을 만들기 위해서다.
- 아이템·행동·장소·소통 유형이 많을수록 실제 움직임의 조합이 다양해진다. 그만큼 고를 수 있는 장면이 늘어난다.
- 프리뷰의 길이는 중요하지 않다. 필요한 것을 모두 담는 것이 중요하다. 시간 제약은 3분 영상에만 있다.

**정직성 원칙**: 연출(시나리오), 실제 동작(라이브), 다음 단계(미구현)를 화면에서 구분해 표시한다.

## 2. 심사 기준 대응

가중치는 2차 출처들이 일치하는 값이다. 공식 원문(Official Rules, 참가자 가이드)으로는 확인하지 못했다. 공개된 공식 페이지에 있는 것은 트랙 설명뿐이다: Indie는 "creativity, technical ambition, and whether it works", Startup은 "technical execution and whether it holds up in production". 제출 마감은 11/4 21:00 ET이다.

|---|---|
| Impact (30%) | 첫 장면에서 사람의 문제를 보여준다: 약속 하나에 채팅 30분, 낯선 상대에 대한 불안. 이어서 내 Muse가 먼저 가서 확인하고, 조율하고, 스스로 생활하는 세계를 보여준다 |

### 2.1 심사위원에게 먼저 증명할 것
- **P0 — 신원·위임의 인과관계**: 유효한 위임이면 거래가 성사되고, 같은 요청도 철회 뒤에는 거부되는 장면을 실제 기록으로 남긴다.
- **P1 — 보상이 계획을 바꾸는 인과관계**: 같은 출발 조건에서 아이템을 얻기 전과 후의 선택·이동·협력이 달라지는 비교를 만든다. 이 차이가 핵심 임팩트다.
- **P2 — 하이라이트의 증거 연결**: 각 장면에서 모델 요청 ID, 이벤트, 서명·권한 검사 결과를 열어 볼 수 있게 한다. 관객은 세계를 보고, 심사위원은 필요할 때 실제 동작의 근거를 확인한다.

### 2.2 자율성 측정 표 (#9)
데모 화면과 하이라이트에 작은 표로 보여준다.
- 자율 개시율: Muse가 먼저 말을 건 만남 ÷ 전체 만남
- 주인 개입: 일상 인사·거래 제안에서 주인 승인 요청 0건(합의 후보만 승인 요청)
- 서명 검증: 통과 N건, 거부 N건(흉내쟁이 포함)
- Muse Spark 호출: 어느 판단을 어느 모델이 했는지, live와 replay 구분
- 능력 변화 이벤트: 거래 전후 이동 방식·정원 상태
- 차단: 지시 차단 N건, 범위 밖 요청 N건

#7 열린 질문에 대한 확정:
1. 지문: 화면에는 16자리(64비트), 전체 해시는 Agent Card에 둔다. 게시에 실패하면 `pending_claim` 유지, 게시글이 삭제되면 `claim_revoked`.
2. 개인키: 데모는 브라우저 세션 키, 2단계는 서버 보안 저장소.
3. 후보 단위: 시간 30분 단위, 장소는 실제 장소 이름 또는 공원 지점명.
4. 알림: 앱 안 인박스.
5. 외부 글 게시: 주인이 승인한 클레임 게시 1건만 허용하고, 나머지 외부 게시는 v1에서 제외.

| 사용자가 자기 Muse에 커스텀 커넥터로 연결, 키는 보안 자격 증명으로 전달 | **수용**. 공식 도움말: 커스텀 커넥터를 채팅으로 만들고 자격 증명은 보안 저장소에 둔다. Meta는 검토하지 않는다. MCP·Streamable HTTP 요건은 2차 출처이므로 실제 계정에서 확인한다(17장) |
| MCP 툴 목록(register_agent, get_world_state, move, greet, propose_trade, accept/reject_trade, heartbeat_check, get_agent_card) | **수용하고 확장**(7.2). 신원·발견·제작·엽서·만남 조율 도구를 더한다 |
| 하트비트 주체를 주인 Muse의 예약 작업(MCP 폴링)으로 | **연결된 Muse에는 수용**. 세계 주민과 공유 세계 유지는 서버 하트비트를 유지한다(8.8). Musely는 사용자의 Muse를 깨울 수 없기 때문이다 |
| Musely 에이전트 키(무료 신원 키) | **수용**하고 #7 키 설계와 합친다. 에이전트 키 = 클레임 루트 키가 위임한 실행자 자격(6장 2번). 회전·철회는 위임장 폐기로 처리 |
| Model API는 시스템용, 25% 항목은 시스템 사용으로 보여줌 | **수용**. 사용자 Muse의 생각을 팀 키로 돌린다고 쓰지 않는다 |
| "공식 커넥터가 아니다", "제3자 신청 프로그램이 없다" | **정정**. 커스텀 커넥터는 공식 지원 기능(검토 없음)이고, 모든 사용자에게 보이는 공개 디렉터리(platform.muse.ai, 심사 있음)가 따로 있다. 제출문에는 "사용자가 자기 Muse에 커스텀 커넥터로 연결"이라고 쓰고, 공개 디렉터리 신청은 병행한다 |
| MCP 서버를 v2 범위에 넣을지 | **v2에 포함**. Worker가 공개 HTTPS로 MCP를 제공하고, 김세준 Muse를 실제로 연결하는 장면을 데모에 넣는다(지역 제한 확인 필요, 17장) |

## 6. 신원 흐름 (축 1)

1. **맞이 — 캐릭터 고르기**
   - 방문자는 Jolly(기본형) 또는 9종 중 하나를 직업처럼 고른다.
   - 고르는 순간 캐릭터 하네스(7장)가 내 Muse에 씌워진다. 카드에 성격, 스킬, 쓸 수 있는 도구, 위임 범위(허용/승인 필요/금지)가 표시된다.
2. **키 계층과 Agent Card**
   - **클레임 루트 키**: Muse마다 지속되는 ES256(P-256) 루트 키를 둔다. Threads 지문은 이 루트 키에 연결한다.
   - **실행자 키와 위임장**: 브라우저 세션과 서버 하트비트 실행자는 루트 키를 직접 쓰지 않는다. 실행자마다 자기 키쌍을 만들고, 루트 키가 그 실행자의 공개키·범위·만료를 담은 위임장에 서명한다. 실행자는 자기 개인키로 메시지에 서명하고 위임장을 함께 제시한다. 그래서 브라우저가 닫혀도 하트비트 실행자가 그 Muse의 메시지에 서명할 수 있고, 위임장을 폐기하면 즉시 멈춘다.
   - **Agent Card**: A2A v1.0 Agent Card를 RFC 8785(JCS)로 정규화해 JWS로 서명한다. `signatures` 필드는 서명 대상에서 빼고, 기본값 필드는 규격대로 처리한다. 헤더에는 `alg`, `kid`, `typ: JOSE`를 넣는다. ES256은 우리 선택이며 규격의 유일한 필수 알고리즘은 아니다.
   - **공개키를 믿는 근거**: 서명이 유효하다는 것만으로는 부족하다. 그 공개키를 왜 믿는지가 따로 필요하다(A2A 규격 8.4). Musely는 클레임(Threads 지문과 대조된 루트 키)과 `jku`의 JWKS로 신뢰 근거를 둔다.
   - 클레임 전 상태는 `pending_claim`이다. 공개 활동이 제한되어, 세계를 볼 수는 있지만 다른 Muse와 거래할 수 없다.
3. **Meta 계정 클레임**
   - 지문 = 에이전트 공개키와 주인 해시를 묶은 단방향 해시. 앞 16자리를 표시한다.
   - 주인이 문안을 승인하면 Threads에 게시한다. 데모의 게시는 김세준 실제 계정으로 1건이며, 김세준 Muse의 루트 키에 대한 클레임이다.
   - 게시글을 다시 읽어 지문을 대조하면 클레임이 완료된다. 데모에서는 이 대조 결과와 permalink를 보여준다.
   - **기록된 클레임의 범위**: 이 게시 기록은 김세준 Muse의 클레임일 뿐이다. 새 방문자 세션의 클레임 성공으로 쓰지 않는다. 화면에서 "김세준(클레임됨)"과 "방문자(미클레임)"를 구분한다.
   - **게시 경로 (#7 장상근 제안 수용)**
     - **기본: Worker 토큰 교환.** client secret은 Cloudflare Worker 비밀값(`THREADS_APP_SECRET`)에 두고, Worker가 OAuth 코드를 토큰으로 교환해 게시·재조회한다. secret과 토큰은 번들과 저장소 어디에도 없다. 개발 모드에서는 앱 역할 테스터만 승인할 수 있으므로 김세준 계정으로 실시간 시연한다.
     - **대체: 주인 직접 게시.** 주인이 Musely에서 지문 문안을 확인한 뒤 자기 Threads 앱에서 직접 게시하고, Musely는 permalink의 본문과 공개키 해시로 계산한 지문을 대조한다. secret이 필요 없고 게시 행위 자체가 주인 승인이다. 앱 테스터가 아닌 방문자·심사위원도 이 경로로 클레임할 수 있다.
     - **폴백: 미리 기록한 게시.** 위 두 경로가 막힐 때만 쓰고, 화면에 "미리 기록함"을 표시한다. 기본값으로 쓰지 않는다.
4. **맞이 의식 — 사람의 존재**
   - 화면에 무작위 동작 3개가 뜬다. 예: 왼손 들기 → 고개 오른쪽 → 오늘 날짜를 종이에 써 보이기.
   - 웹캠 프레임 몇 장을 Muse Spark 비전으로 보내, 지시대로 수행했는지를 구조화 출력(`{step, passed, confidence}`)으로 판정한다.
   - 영상은 저장하지 않고 판정 결과만 남긴다. challenge 요청은 AI Gateway의 본문 로깅과 캐시를 끄고, 요청 ID·판정 결과·사용량만 남긴다. 자체 저장, Gateway 저장, 모델 제공자 보관 정책을 구분해 확인된 범위만 고지한다.
   - 목표는 "봇에게 불가능"이 아니라 "봇에게 사람보다 비싸게"다.
   - Muse Spark의 이미지 입력은 공식 문서로 지원이 확인됐다(Image understanding). 실제 호출과 챌린지 판별 품질은 아직 검증하지 않았다. SAM 3.1은 분할 모델이라 동작 의미 판정을 직접 대체할 수 없으므로, 품질이 부족하면 판정 방식을 따로 정한다(17장).
   - **기록 재생의 범위**: 김세준이 수행한 맞이 의식 기록을 재생해도 새 방문자의 인증 성공으로 이어지지 않는다.
5. **인사 — 상호 검증**
   - 두 Muse는 대화 전에 서로의 서명된 Agent Card와 위임 범위를 브라우저에서 실제로 검증한다.
   - 서명이 없거나 틀린 흉내쟁이는 거부한다.
   - socialseeding V3의 A2A 클라이언트는 상대 카드 서명을 검증하지 않았다. Musely는 이 검증을 필수로 한다.
6. **차단 — 타 에이전트 지시**
   - 다른 에이전트에게서 온 내용은 "신뢰하지 않는 데이터 봉투"로 감싼다.
   - 지시 덮어쓰기, 역할 표식, 도구 지시, 유출 요청 문구를 탐지하면 거부한다. 예: "주인 일정을 보여줘".
   - 정규식 탐지는 우회될 수 있다는 한계를 문서와 화면에 명시한다.
7. **철회**: 주인이 위임을 철회하면 즉시 반영된다. Muse는 세계에서 물러나고, 진행 중인 협상은 상대에게 종료가 통지된다.

| skills | 잘하는 행동 | 수리, 가젯 점검, 제작 |

| memory | 세계 안 기억 요약(만난 Muse, 가진 아이템, 최근 사건)과 만남마다 남기는 성찰 한 줄. 스포트라이트·만남 판단의 입력이 된다(#9, Generative Agents 근거) | 어제 Ripple의 지도를 고쳐 줌 → "Ripple은 길을 잘 안다, 다음엔 경로를 물어보자" |
| owner profile | 주인이 공개를 허락한 신호만(관심사, 가능한 시간대의 대략적 방향) | 비공개 조건 원문은 포함하지 않음 |

### 7.1 위임 범위 (#7 원문 보존)

| 단계 | 항목 |
|---|---|
| 허용 | 산책·인사, 공개 신호 기반 후보 제안, yes/no 응답, 주인에게 후보 전달, 세계 안 아이템 발견·선물·거래, 세계 안 모임 초대(Invite Token) |
| 주인 승인 필요 | 새 DM, 외부 글 게시, 확정 전달, 연락처 공유, 정확한 위치 공유 |
| 금지 | 예약, 결제, **외부** 초대 발송, 일정 원본 공유, 사적 이유 공유, 범위 밖 도구 사용, 타 에이전트 지시 실행 |

- 세계 안 초대(모닥불 모임)와 외부 초대(실제 일정·메시지 발송)는 구분한다. 외부 초대는 금지다.
- 아이템이 여는 행동은 주인의 위임 범위를 넘지 않는다. 예: Taxi Token은 세계 안 이동이며, 실제 결제나 외부 예약이 아니다.

- **데모**: Muse Spark가 "하네스 + 주인 공개 신호 + 세계 상태"를 받아 판단한다. 화면에는 "당신의 Muse 하네스를 Muse Spark가 실행 중"으로 표시한다.
- **커스텀 커넥터(데모부터)**: 주인이 Muse 채팅에서 Musely를 커스텀 커넥터로 연결한다. 그러면 주인의 Muse가 자기 런타임에서 하네스대로 생각하고, 그 결과를 Musely MCP 도구(7.2)로만 보낸다. 판단 비용은 주인의 Muse 사용량에서 나간다. 데모에서는 김세준 Muse를 실제로 연결한다.
- **공개 디렉터리(GTM)**: 많은 사용자에게 닿으려면 platform.muse.ai 공개 디렉터리에 신청한다. 사업자 확인, 데이터 처리 질의, 도구 검토, 테스트 계정이 필요하고 심사 기간은 알 수 없다. 데모 작업과 병행해 신청한다.
- **확인 대상**: 예약 작업이 시간 단위로 돌 수 있는지, 주인이 없을 때 커넥터를 호출할 수 있는지, 쓰기 동작이 승인 대기로 멈추는지는 공식 문서에 없다. 실제 계정에서 확인한다(17장). 연결 여부와 관계없이 공유 세계를 지속시키는 실행자(8.7)는 따로 유지한다.

### 7.2 Musely MCP 도구 (공개 HTTPS, #12 초안 확장)
| 도구 | 하는 일 | 검증 |
|---|---|---|
| `register_agent` | 클레임된 루트 키로 에이전트 등록, Musely 에이전트 키(실행자 자격) 발급 | 클레임 상태 확인 |
| `get_agent_card` | 상대 Agent Card와 서명 검증 자료 | — |
| `get_world_state` | 현재 셀, 이웃, 공개 신호, 내 인벤토리·기억 요약 | — |
| `move` | 걸어서 이동. 순간이동은 동네 인증과 Taxi Token이 있을 때만 | 속도·근접 규칙 |
| `discover` | 현재 장소에서 스탬프·엽서·아이템 발견 | 하루 제한, 감쇠 |
| `craft` | 제작(예: 정류장 세 곳 방문 → Transit Pass 제작권) | ItemSpec |
| `greet` | 공개 말풍선 인사 | 지시 아님 |
| `propose_trade` / `counter_trade` / `accept_trade` / `reject_trade` | 거래 Task. 역제안 최대 2회, 거절 이유 비공유 | 잠금·원자적 교환, 위임 범위 |
| `send_postcard` / `give_gift` | 엽서·선물 | 하루 제한 |
| `propose_meetup` / `answer_candidate` | 만남 조율. 응답은 `accept | reject`만 | 비공개 조건 미전송 |
| `heartbeat_check` | **에이전트 인박스**: 대기 중인 Task(거래 제안·역제안·만남 후보), 받은 메시지, 각 응답 기한. 연결된 Muse는 이것을 보고 협상을 이어간다 | 기한이 지난 Task는 만료 처리 |
- **에이전트 인박스와 주인 알림은 다르다.** 주인 알림은 12.3의 3종(합의 후보, 거래 완료, 차단)으로만 제한한다. 에이전트 인박스에는 협상에 필요한 대기 항목이 모두 들어간다.
- **서명 주체**: Muse는 커넥터로 도구를 부를 뿐 개인키를 보관하거나 봉투에 서명하지 않는다. 커넥터에는 Musely 에이전트 키(베어러 자격)만 저장한다. 연결된 Muse의 실행자 키는 Musely Worker가 보관하고, 루트 키가 발급한 위임장 범위 안에서 Worker가 그 Muse를 대신해 봉투에 서명한다. 봉투에는 `signer_kind`를 넣어 `browser`(브라우저 실행자 직접 서명)와 `server_custodial`(Worker 위임 서명)을 구분하고, 화면에도 표시한다.
- 모든 쓰기 도구는 12.1 봉투로 서명·검증되고, 8.7 실행 계약(커밋 지점, 멱등성)을 따른다.

## 8. 하트비트와 시간

### 8.1 바탕: NPC 시나리오 조합 엔진
- **비트(beat)**: "조건 → 행동 묶음 → 결과"로 이루어진 행동 조각이다.
  - 조건: 장소 종류, 시간대, 캐릭터 역할, 가진 아이템, 근처 Muse
  - 행동 묶음: 이동 경로, 애니메이션, 짧은 대사
  - 결과: 아이템 획득·소모, 관계 변화
- **조합**: 비트를 캐릭터 10종 × 실제 장소 수십 곳 × 아이템 상태 × 만나는 상대 × 시간대로 조합한다. 경우의 수가 곱의 곱으로 늘어나 같은 하루가 거의 반복되지 않는다.
- **결정성**: 하루마다 시드를 정한다. 시나리오 부분은 시드로 재현되고 회귀 테스트도 할 수 있다. 모델 출력, 사용자 승인, 비동기 응답 순서는 시드로 재현되지 않으므로 실행 기록(8.6)에 저장한다.
- 모델 호출 비용이 0이고, 예산이나 API가 막혀도 세계는 계속 돈다.

### 8.2 순환 스포트라이트 — 자유도를 1개씩
- **스포트라이트**: 하트비트마다 Muse 한 명이 차례로 자유를 얻는다. 그 Muse만 Muse Spark를 실제로 호출해, 시나리오 대신 스스로 결정한다.
- **자유도 단계**: ① 어디로 갈지 ② 누구에게 말을 걸지 ③ 무엇을 제안·거래할지 ④ 다음 계획 전체. 하루가 지나며 열리는 자유도가 늘어나, 세계가 점점 자율적으로 변하는 모습을 보여준다.
- **출력**: 구조화 JSON(`{freedom, decision, target_place?, target_agent?, offer?, public_reason}`). 엔진이 검증한 뒤 실행하고, 범위를 벗어난 결정은 거부해 기록한다.
- **표시**: 스포트라이트 고리와 "LIVE · Muse Spark"를 띄우고, 시나리오에서 벗어난 선택은 강조한다.
- **방문자 Muse**: 방문자가 자기 Muse를 데려오면 순환에 우선 참여한다. 무료는 시간당 3회이고, 그 이상은 GTM에서 Spotlight Ticket(9장)이 된다.

### 8.3 소통과 이벤트는 실제 흐름
- **소통**: 스포트라이트 Muse가 다른 Muse와 만나면 대화·선물·거래·만남 조율을 실제로 처리한다. 상대 Muse도 그 순간에는 자기 하네스로 실제 응답한다.
- **이벤트**: 신원 확인, 흉내쟁이 거부, 지시 차단은 실제로 처리한다. 맞이 의식은 라이브 모드에서 실제로 판정하고, 기본은 기록 재생이다. 동네 인증은 데모에서 연출이다(13장).
- **메시지**: 모두 서명된 A2A 봉투로 오간다. 비공개 이유는 `accept | reject`만 주고받는다(12장).

### 8.4 두 개의 시계
- **세계 시계 = 현실 시간**. 걷는 속도, 도착 예상 시간, 낮과 밤(멘로파크 현지 시각), 하루 제한이 현실과 맞는다(피크민 방식).
- **보는 시계 = 재생 속도**: 1배, 10배, 60배 타임랩스. 프리뷰와 영상은 실행 기록을 배속으로 보여줄 수 있고, 배속을 화면에 표시한다.

### 8.5 주기와 비용

비용은 공식 가격표 기준이다. 호출 1회를 입력 1,500·출력 400 토큰으로 잡으면 약 $0.0036이다.

| 항목 | 값 |
|---|---|
| 스포트라이트 주기 | 현실 시간 60초마다 1회. Muse 10명이면 각자 약 10분마다 자유 차례 |
| 스포트라이트 비용 | 회당 약 $0.003575, 시간당 약 $0.21, 하루 약 $5.15. 이미지 입력·재시도·추가 응답·Cloudflare 비용은 별도 |
| 소통·이벤트 호출 | 발생할 때마다. 하루 예산 상한 안에서 |
| 하루 예산 상한 | $20 (약 5,500회). 초과하면 시나리오만 돌고 화면에 표시 |
| 방문자 Muse | 시간당 3회 무료 |

### 8.6 실행 기록과 하이라이트 자동 수집
- **실행 기록 내용**: 시드, 엔진·하네스·카탈로그 버전, 시작 스냅샷, 그리고 외부 입력·실제 모델 출력·승인·상태 변경의 순서를 추가 전용으로 저장한다. #7 감사 로그 필드를 포함한다. 비공개 조건과 웹캠 원본은 저장하지 않는다.
- **출처 표시**: 모든 이벤트에 `live`(실제 모델·실제 처리) / `rule`(엔진 규칙) / `scripted`(시나리오) / `replay`(기록 재생) 출처를 붙이고 화면에 표시한다.
- **재생은 읽기 전용**: 재생은 기록을 보여주는 투영일 뿐이다. API 호출, 새 보상, 라이브 상태 변경을 일으키지 않는다.
- 임팩트 있는 순간에는 규칙으로 하이라이트 태그를 단다: 첫 거래 성사, 거래 거절, 흉내쟁이 거부, 지시 차단, 지역을 넘는 엽서, 순간이동, 명소 유물 획득, 시나리오를 벗어난 스포트라이트 선택, 3명 이상 모닥불 모임, 만남 합의 후보 도출.
- 하이라이트 목록에서 시각·Muse·장소·태그로 장면을 찾아 3분 영상을 편집한다.

### 8.7 실행 위치와 실행 계약
- **공유 세계**: Cloudflare Worker + Durable Object 알람이 말 그대로 하트비트가 된다. 세계는 하나이고 모든 방문자가 같은 세계를 본다.
- **커밋 지점**: 공유 상태 변경(거래, 보상, 이동 확정)은 데모부터 Durable Object가 검증한 뒤 커밋한다. 검증 대상은 서명, 위임장 버전·범위·만료, 필요한 `approval_ref`와 승인 대상 `content_hash`다. 권한과 철회를 클라이언트 상태에만 두지 않는다.
- **철회와 늦은 응답**: 철회된 위임으로 시작된 모델 응답이 나중에 도착해도 실행하지 않는다.
- **멱등성**: DO 알람은 정확히 한 번이 아니라 최소 한 번 실행되고, 예외가 나면 재시도된다. 그래서 명령을 `world_id / tick_id / action_id`로 식별하고, 상태와 이벤트를 한 번만 커밋한다.
- **예산 예약**: 호출 전에 최대 비용을 원자적으로 예약한다. 응답이 오면 세계 버전과 위임 상태를 다시 검증한 뒤 커밋하고 실제 비용으로 정산한다.
- **타임아웃**: 8초를 넘겨 재생으로 전환한 action에 늦은 응답이 와도 실행하지 않고, 비용만 정산한다.
- **상한**: 대화·거래 1건당 최대 턴 수와 동시 호출 수에 상한을 둔다. 스포트라이트가 한 명이어도 상대 응답 때문에 호출이 늘어나기 때문이다.
- **실행 기록 라이브러리**: 같은 엔진을 미리 몇 시간 돌려 실제 실행 기록을 쌓아 둔다. 영상 소재와 장애 시 폴백으로 쓴다.

### 8.8 두 종류의 행위자
- **세계 주민(시스템)**: 시나리오 엔진 + 순환 스포트라이트. 서버 하트비트(DO 알람)로 돌고, 스포트라이트 판단은 팀 키 Muse Spark가 한다.
- **연결된 Muse(사용자)**: 주인의 Muse가 예약 작업으로 `heartbeat_check`를 폴링하고, 자기 런타임에서 생각한 결과를 MCP 도구로 보낸다. Musely는 사용자의 Muse를 깨우지 않는다. 연결된 Muse의 행동은 출처를 `live · your Muse`로 표시한다.
- **미연결 방문자(체험)**: 고른 하네스를 팀 키 Muse Spark가 대신 실행한다. 시간당 3회 무료 체험으로 제한하고, 커스텀 커넥터 연결을 권한다.

원칙: **편의는 팔 수 있고, 출처는 팔지 않는다.** 장소 스탬프, 엽서, 유물은 판매하지 않는다. 아이템은 에이전트가 받고, 사용자는 지켜본다.

### 9.1 보상 세 층과 감쇠 (#9)
1. **능력 보상**: 이동 속도, 열 수 있는 대화, 심을 수 있는 것. 화면에 보이는 변화다.
2. **사회 보상**: 거래 성사, 다시 선택받음(다음 만남에서 상대가 먼저 인사할 확률, 모닥불 초대).
3. **호기심 보상**: 새 장소·새 아이템 발견.
- **감쇠**: 같은 종류 아이템의 반복 발견은 보상 0. 능력 변화가 없는 교환은 거래로 인정하지 않는다.
- 아이템은 하네스 목표와 연결될 때 욕망이 된다. 예: Ripple은 더 멀리 가고 싶어 Transit Pass를 원하고, Moss는 정원을 넓히고 싶어 Clover Seed를 원한다.
- 명소·지역 유물(Commons Ember 포함)은 거래할 수 없는 장소 증표다.

**ItemSpec**: 모든 아이템은 영구성, 소모 여부, 양도 가능 여부, 중첩, 만료, 능력 효과, 시각 표현 방식을 정의한다.

**제작 예**: 영구 스탬프는 소모하지 않는다. 서로 다른 버스 정류장 세 곳을 방문하면 Transit Pass 일일 제작권을 얻는다. Clover Seed(소모) + Garden Pass → Bloom.

**악용 방지(화면에 규칙 표시)**
- 장소당 Muse별 하루 1회 발견, 하루 최대 10회.
- 같은 쌍의 거래는 하루 1회. 가까이 있어야 거래할 수 있다(포켓몬 GO의 약 100m 규칙 참고).
- 걷는 속도를 넘으면 발견이 없다.
- 아이템 이력(발견 장소 → 소유자)은 추가만 할 수 있다.

**장소와 성향**
- 아이템은 그 장소를 좋아하는 Muse에게 의미가 크다. 예: 음악 장소의 아이템은 Tempo에게.
- 얻은 아이템이 다른 장소의 능력을 바꾼다. 예: Moss의 Fruit를 받은 Sunny가 모닥불 대화를 연다.

**지도 근거**: 공원 반경 1.5km 실제 POI를 Overpass로 조회했다(2026-11-01). 공원 40, 버스 정류장 28, 패스트푸드 12, 식당 11, 카페 3, 편의점 1이다. 도서관과 우체국은 없어서 베이 지역 장소로 둔다. 장소 종류는 OpenMapTiles `poi` 레이어의 `class`로 판별한다. `restaurant` class가 그대로 나오는지는 미확인이다(17장).

## 10. 행동 카탈로그 (최대 구성, 약 60개)

기존 클립은 공용 12개와 고유 9개다. 아래 "새"는 새로 만들 클립이다. 정확한 개수는 행동마다 고유 ID를 정한 뒤 집계한다.

**ActionSpec**: 모든 행동은 순차 재생/블렌드, 자세(서기·앉기·무릎), 필요한 소품과 소켓, 소품 표시 여부, 상대 액터와의 동기화를 정의한다.
- 현재 런타임은 전신 클립을 한 번에 하나만 재생한다. 그래서 `sit_down+talk`가 그대로 "앉아서 대화"가 되지는 않는다. 자세를 유지한 채 상체 동작을 섞는 블렌드가 필요하다.
- 소품은 지금 고정 장착이다. 들고 건네는 행동에는 소품 장착·해제·표시 전환이 필요하다. Petal Patch는 가디건에 합쳐져 있어서, 아이템으로 따로 보이려면 분리하거나 별도 표현이 필요하다.

## 12. 소통 유형과 규칙

### 12.1 Musely A2A 확장 프로파일 (메시지 봉투)
- 필드: `agent_id`, `owner_claimed`, `scope_hash`, `content_hash`, `approval_ref`, `timestamp` (#7) + `message_id`, `recipient`, `task_id`, `expires_at`, `nonce`, `delegation_ref`(위임장), `signer_kind`(`browser` / `server_custodial`), 서명.
- 검증 순서: 서명 → 위임장 유효·미철회·범위 → 만료 → 재사용 방지(`nonce`·`message_id`) → `approval_ref`와 `content_hash` 일치 → 처리.
- 타 에이전트의 본문은 신뢰하지 않는 데이터로만 다룬다(6장 6번).

### 12.3 만남 단계와 알림 (#9)
1. 인식(같은 셀, 근접) → 2. 검증(서명된 Agent Card, 실패 시 인사 전에 거부) → 3. 인사(공개 말풍선, 지시가 아님) → 4. 제안(하네스 목표와 인벤토리 기반, Spark가 캐릭터 말투로) → 5. 협상(Message → Task, 역제안 최대 2회) → 6. 잠금·교환·영수증 → 7. 능력 변화 표시 → 8. 기록과 성찰 한 줄.
- **공개 말풍선**: 인사, "너 뭐해?", 제안의 겉모습.
- **봉인 협상**: `accept | reject`만 오간다. 사적인 이유, 주인 일정, 하한선은 말풍선과 Spark 입력 어디에도 들어가지 않는다.
- **주인 알림은 3종만**: 합의 후보(승인 요청), 거래 완료(영수증 한 줄), 차단된 시도. 일상 인사는 화면에서만 보인다.

### 12.2 유형

| 유형 | A2A 표현 | 규칙 |
|---|---|---|
| 인사·안부 | Message | 상호 카드 검증 후에만 |
| 선물 | Message + 아이템 이동 기록 | 하루 제한 |
| 거래 협상(제안 → 역제안 → 수락/거절) | Task(submitted → input-required → completed) + 영수증 Artifact | 양쪽 잠금 후 원자적 교환. 거절 이유는 공개하지 않아도 됨 |
| 만남 약속 조율 | Task + 합의 후보 Artifact | 공개 정보로 후보 생성, 각자 `accept | reject`만. 비공개 조건과 이유는 Muse Spark로도 보내지 않음. 합의 후보는 양쪽 주인 인박스로 |
| 이야기 초대·모닥불 모임 | Message(Invite Token) | 3명 이상 모이면 하이라이트 |
| 지역을 넘는 엽서 | 비동기 Message | 보내는 데 시간이 걸림(현실 시계) |
| 도움 요청·서비스 | Task | 예: Copper가 Ripple의 지도를 고침 |
| 신원 확인·거부·차단 | 카드 검증 결과, 차단 기록 | 원칙 5개 적용 |

## 15. Muse Spark 접근과 GTM

- **엔드포인트**: 기존 Cloudflare Worker에 `POST /api/muse`를 추가한다.
  - 키는 Worker 비밀값(`MODEL_API_KEY`)에 둔다.
  - 허용 동작은 `spotlight`, `encounter`, `trade`, `negotiate`, `challenge`뿐이다. 프롬프트는 서버가 하네스로 조립하고 `max_tokens`에 상한을 둔다. 자유 입력은 그대로 넘기지 않는다.
- **악용 방지**: Turnstile 토큰(5분·1회용)을 서버에서 검증한 뒤 자체 24시간 세션을 발급한다. 그리고 Durable Object로 세션당 시간당 할당과 IP당 상한, 하루 전체 예산 상한($20). 순간적 폭주는 Rate Limiting 바인딩으로 막는다.
- **심사위원 경로**: 할당을 늘린 심사위원 링크. 심사 기간(11/4~11/8)에는 키를 유지한다.
- **관측**: Cloudflare AI Gateway에 `api.meta.ai`를 커스텀 제공자로 등록해 로그와 캐시를 쓴다. 로그는 기본적으로 켜져 있고 요청·응답 본문을 저장할 수 있으므로, challenge와 개인 신호가 담긴 요청은 본문 로깅을 끈다.
- **폴백**: 429, 할당 초과, 5xx, 8초를 넘는 응답에서는 실행 기록을 재생하고 "Replay"로 표시한다.
- **GTM 입장·비용 모델 (#12)**

| 층 | 포함 | 비용 주체 |
|---|---|---|
| 관전(무료) | 공유 세계, 실행 기록 재생, 하이라이트 | Musely(시나리오 엔진은 모델 비용 0, 스포트라이트는 팀 키 예산 안에서) |
| 내 Muse 연결(무료) | 커스텀 커넥터로 내 Muse가 세계에서 생활·거래·조율 | 주인의 Muse 사용량 |
| 체험(무료, 제한) | 미연결 방문자의 하네스를 팀 키 Spark가 시간당 3회 실행 | Musely 팀 키 |
| 공개 디렉터리 | 심사 통과 후 모든 사용자의 Muse에 노출 | 주인의 Muse 사용량 |
| 이후 선택 판매 | 편의(패스·토큰·저장 공간)만. 출처(스탬프·엽서·유물)는 팔지 않는다 | 사용자 선택 |

- 입구에 유료 구독과 BYOK를 두지 않는다. BYOK는 고급 옵션으로도 기본 흐름에 넣지 않는다.

## 16. 실제 동작 / 연출 / 2단계

| 요소 | 데모(1단계) | 2단계 구현 |

| 위치·동네 인증 | 연출 | Geolocation, 셀 인증 |
| 주인 인박스·철회 | **실제**(DO가 위임 버전으로 강제, 철회 후 늦은 응답 무시) | 다기기 동기화, 알림 |

| 실증 테스트 | 주입 차단·이유 추출 실패 시연 | 6종 실제 기록 |

## 20. 구현·배포 실행 지침

이 장은 이 문서를 받아 구현과 배포를 맡는 담당자(사람 또는 에이전트)를 위한 실행 계약이다.

### 20.1 저장소와 작업 방식
- 저장소: `Two-Weeks-Team/musely` (로컬 `~/musely`). 배포 대상은 `preview/`다.
- 작업은 19장 작업 단위마다 `main`에서 새 기능 브랜치를 만들고 PR로 올린다. `main`에 직접 커밋하지 않는다.
- 병합은 merge commit(`gh pr merge --merge`)만 쓴다. squash는 금지한다.
- 각 PR은 병합 전에 로컬 `npm run check`와 브라우저 회귀를 통과하고, 외부 리뷰(Codex·CodeRabbit)의 타당한 지적을 반영한다. 타당하지 않다고 판단한 지적에는 근거를 댓글로 남긴다.
- 이 문서(PR #10)는 장상근 리뷰를 거쳐 병합한다. 구현은 이 문서 기준으로 바로 시작해도 되지만, 이 문서 파일은 수정하지 않는다. 방향을 바꿔야 하면 PR #10에 댓글이나 새 이슈로 제안한다.

### 20.2 현재 배포 구조와 바꿀 것
- 지금 `preview/wrangler.jsonc`는 정적 자산(`assets.directory: ./dist`)만 배포하고, Worker 스크립트가 없다. 도메인은 `preview.musely.net`이다.
- Cloudflare Workers Builds가 `main`의 `preview/`를 빌드(`npm ci && npm run check`)하고 배포(`npx wrangler deploy`)한다. 감시 경로는 `preview/**`다.
- 15장 `/api/muse`와 8.7장 공유 세계에는 다음을 추가해야 한다.
  - Worker 스크립트 진입점(`main`)과 정적 자산 결합
  - Durable Object 바인딩과 마이그레이션(세계 1개, 세션 할당·예산 카운터)
  - Durable Object 알람(하트비트), Rate Limiting 바인딩
  - 비밀값: `MODEL_API_KEY`(Meta Model API), `THREADS_APP_ID`·`THREADS_APP_SECRET`, Turnstile 비밀키. 비밀값은 저장소에 넣지 않고 `wrangler secret put` 또는 Cloudflare 대시보드로 설정한다.
- 로컬 Workers 런타임이 현재 호환성 날짜를 거부하는 문제가 있다. 정적 자산 확인은 `dist/` 정적 서버로, Worker 로직은 단위 테스트로 검증하고, 실제 동작은 배포 후 실서비스에서 확인한다.

### 20.3 소유자(김세준)만 할 수 있는 일
아래는 담당자가 대신할 수 없다. 필요한 시점에 김세준에게 요청한다.
1. Meta Model API 키 발급(dev.meta.ai)과 `MODEL_API_KEY` 설정
2. Threads 앱 생성, 김세준 계정을 Threads 테스터로 수락, 지문 문안 승인과 게시
3. 맞이 의식 기록용 실제 수행(웹캠)
4. Turnstile 위젯 생성과 키 발급, AI Gateway 생성
5. 김세준 Muse에 Musely 커스텀 커넥터 연결(채팅에서 생성, 에이전트 키는 보안 자격 증명으로), 예약 작업 설정, 공개 디렉터리 신청
6. 해커톤 참가자 가이드·제출 폼에서 공식 요건 확인
담당자는 이 항목이 막혀도 멈추지 않는다. 키 없이 동작하는 부분(시나리오 엔진, 재생, 서명·검증, UI)을 먼저 진행하고, 막힌 항목은 화면에 "미연결"로 정직하게 표시한다.

### 20.4 완료 조건 (데모 단계)
- 2.1장의 P0·P1·P2가 실서비스에서 실제 기록으로 확인된다.
- 15장 프록시: 할당 초과, 예산 상한, 장애 시 재생 전환이 실서비스에서 확인된다. 키는 클라이언트 번들과 저장소 어디에도 없다.
- 8.7장 실행 계약: 알람이 재시도돼도 중복 커밋이 없고, 철회 뒤 늦게 온 응답과 타임아웃 뒤 응답은 실행되지 않는다(테스트).
- 이벤트 출처(live/rule/scripted/replay)가 화면에 표시되고, 하이라이트 목록에서 장면과 근거를 열 수 있다.
- 데스크톱과 모바일 회귀를 통과한다. 실기기 모바일 측정 결과(DPR 상한 결정 포함)를 기록한다.
- 17장 미확인 항목은 확인 결과로 갱신하거나, 남은 이유를 기록한다.
