# Musely — PRD (마일스톤 기반, 세계: Museion)

> **상태 (2026-11-01 갱신): 현재 구현 기준으로 방향을 고친 PRD.** 2.1절에 마일스톤별 현재 구현 상태를 추가하고, M2(무대)를 실제 구현인 지도 위 공원과 10종 캐릭터 기준으로 다시 썼다. 나머지 마일스톤(M0·M1·M3~M8)의 요구사항은 아직 구현되지 않은 계획이다. 문서 간 관계는 [`docs/README.md`](README.md).

기획안(`museion-plan-final-2026-10-30.md`)과 개발계획(`museion-dev-plan-2026-10-30.md`)을 실행 단위로 재구성한 제품 요구사항 문서다. 마일스톤은 달력 일정이 아니라 **선행 관계와 완료 게이트**로 정의한다 — 각 마일스톤은 진입 조건을 충족할 때 시작하고, 수용 기준을 전부 통과해야 다음 마일스톤의 진입 조건이 된다.

**진행 방식은 3단계다.** ① POC 단계 — 되는지가 불확실한 지점 일곱 곳을 최소 구현으로 먼저 찔러 통과/탈락을 판정한다 (3장). ② 부분 완성 단계 — POC를 통과한 설계만 마일스톤 단위로 완성하고 각자 테스트한다 (4장). ③ 통합 단계 — 부분들을 합쳐 전 경로 E2E와 제출 게이트를 통과시킨다 (5장). POC에서 탈락한 지점은 본구현에 들어가지 않고, 먼저 설계를 바꿔 다시 판정한다.

**문서 규칙**
- 요구사항 ID: 기능 `FR-<마일스톤>.<번호>`, 비기능 `NFR-<번호>`. 수용 기준은 전부 검증 가능한 문장으로 쓴다.
- "완료"는 수용 기준 통과를 뜻한다. 부분 구현·목업은 완료로 치지 않는다.
- 확정 파라미터(개발계획 4.8)는 이 문서에서 다시 정의하지 않고 참조한다: 조정 최대 5회 / 온도 30.0°~50.0°·시작 36.5°·고위험 하한 40.0° / 불 생성 체크인 7일 20회·소셜 일 10건 / 하네스 3종(Scout·Fixer·Guardian).

## 1. 제품 개요

### 1.1 제품 정의
**Musely**는 현실 장소 위에 겹친 '영감이 모이는 층' Museion에서, 사람마다 하나씩 깃든 AI 에이전트(Muse)가 모닥불 앞에서 서로의 신원(문장)을 확인하고, 비공개 조건을 드러내지 않는 봉인 조율으로 만남 조건을 조율하며, 완료된 만남을 불씨와 온도로 축적하는 서비스. 사용자는 스마트폰·노트북 웹앱으로 그 층을 들여다보고 참여한다.

### 1.2 목표
1. 핵심 경로(맞이하기 → 불 앞에 앉기 → 인사·문장 검증 → 스파크 봉인 조율 → 현장 확인 → 불씨 나누기)가 실제 Meta Model API 호출로 끝까지 동작하는 제품.
2. 비공개 제약이 조율 전 과정에서 원문으로 네트워크를 타지 않는다는 것을 테스트로 증명 가능한 구조.
3. 3분 데모 영상(영어 VO)의 전 장면을 실제 구동 화면으로 촬영할 수 있는 상태.

### 1.3 비목표 (이번 범위에 넣지 않는 것)
- 실제 결제·송금 실행 (에이전트가 금전을 이동시키는 경로는 만들지 않는다 — 기획안 8장)
- 불씨의 거래·이전 기능 (불씨는 양도 불가)
- 온도 가중치 세부 수치의 공개 (조작 방지)
- Gadget SDK 브리지의 상용화 (데모·개인 채널로 한정)
- 네이티브 앱 (반응형 단일 웹앱만)
- 자체 호스팅 추론 모델 (전부 Model API — 2026-10-30 확정)

### 1.4 사용자
- 1차: 주인공 페르소나 "지민"(29세, 사람 만날 일이 많은 사람) — 약속 한 번 잡는 데 채팅 30분을 쓰는 사람. 프리뷰 대본의 주인공이기도 하다 (Jolly를 입은 지민의 Muse).
- 데모 계정: 사전 설정된 2개 계정(노트북·폰 각 1대)으로 전 경로를 재현한다.
- 파일럿: 만남 약속을 자주 잡는 사람 6명 (M7에서 수행).

### 1.5 성공 지표 (측정 방법 포함)
| 지표 | 측정 |
|---|---|
| 핵심 경로 E2E 성공률 | 자동화 체크리스트 전 항목 통과 (5장 전역 게이트) |
| 조율 비공개성 | 패킷 덤프에서 제약 원문 0건 (M4 수용 기준) |
| 합의 후보까지 조정 횟수 분포 | 세션 로그 집계 — 5회 내 합의 후보 도출 또는 정직한 조율 불가 선언 |
| 파일럿 관찰 | 합의 소요 시간·불안 척도(1–10)·합의 성립 여부·확신도 (기획안 7장, 통계 주장 금지) |
| 성능 | 기준 기기 MacBook Air M1에서 2.3 성능 예산 대조 계측 (NFR-1) |

## 3. POC 단계 — 실제 가능성 확인 (본구현 진입 전)

일곱 개 스파이크는 전부 "되면 본구현, 안 되면 설계 변경"이 갈리는 지점이다. 공통 규칙:

- 스파이크 코드는 최소 구현으로 만들고, 본구현에 그대로 가져가지 않는다 (판정 근거와 인터페이스 교훈만 가져간다).
- 각 POC는 시작 전에 통과/탈락 기준을 이 문서의 문장 그대로 고정한다. 결과를 본 뒤 기준을 바꾸지 않는다.
- 판정 결과(통과/조건부/탈락 + 근거 수치)는 수행 당일 리포에 기록한다. 기록 없는 POC는 하지 않은 것이다.
- 탈락 시에는 "탈락 시 변경" 열의 설계로 교체하고, 교체된 설계가 다시 POC 대상인지 판단한다.

### POC-1. Model API 실호출
- **확인할 것.** 모델 5종(`muse-spark-1.3`, `muse-wonder-1.0`, `muse-image-1.0`, `muse-voice-transcribe-1.0`, `sam-3.1`)이 문서 사양대로 붙는가. 특히 미확정인 두 가지 — Voice Transcribe의 실시간 전사 형태, SAM 3.1 분리 출력의 형식 — 을 실응답으로 확정한다. 구조화 출력(JSON Schema) 수신 1건 포함.
- **통과.** 5종 전부 응답 성공 + 응답 형식이 게이트웨이 어댑터로 감쌀 수 있는 형태.
- **탈락 시 변경.** 실패한 모델의 기능은 강등 설계로 교체한다 — Voice 실패 시 조건 입력은 타이핑 전제, SAM 실패 시 수동 크롭이 기본값. 모델 단위 기능은 M0의 어댑터 경계 안에서만 바뀐다.
- **선행 조건.** API 키 + 결제수단. 키가 없으면 어댑터·문서 대조까지만 수행하고 판정은 "보류(미검증)"로 남긴다 — 추측으로 통과 처리하지 않는다.

### POC-2. 봉인 조율 루프
- **확인할 것.** 제품의 중심 주장. UI 없이 스크립트로: 공개 신호 → Muse Spark 후보 생성 → 양쪽 로컬 판정(규칙 기반) → 조정 루프 → 종료. 시나리오 3종을 돌린다: ① 즉시 조율 가능 ② 조정 후 합의 후보 ③ 조율 불가.
- **통과.** 3종 모두 기대한 종료 상태(합의 후보/합의 후보/조율 불가)에 도달하고, 전 과정 트래픽에 제약 원문이 없다.
- **탈락 시 변경.** 후보 생성을 규칙 기반 템플릿 중심으로 재설계하고 Spark는 문장 다듬기 보조로 강등한다. 프로토콜 자체(제안·수락/거부·5회 상한)는 유지한다.

### POC-3. 현장 확인 품질
- **확인할 것.** 실제 물건 사진 3쌍(일치/불일치/판단 어려움)으로 SAM 3.1 분리 → Muse Spark 비전 대조를 돌려, 결과가 데모에서 쓸 수준인지.
- **통과.** 일치·불일치가 구분되고, 판단 어려운 쌍은 "확인 불가"로 정직하게 나온다.
- **탈락 시 변경.** 현장 확인의 중심을 "사람 확인 + 전사 기록"으로 옮기고 비전 대조는 보조 표시로 강등한다 (M5 범위 조정).

### POC-4. 디오라마 성능
- **확인할 것.** 기존 샘플 씬에 아바타 8체·파티클·반경 링·말풍선을 얹은 상태에서 기준 기기(MacBook Air M1) 실브라우저 프레임이 유지되는가.
- **통과.** 품질 강등 없이 55fps 이상, 또는 강등 1단계 안에 60fps 도달. draw call ≤ 50 동시 충족.
- **탈락 시 변경.** 소품·파티클 예산을 하향 재설정한다. 그래도 안 되면 아바타를 빌보드 스프라이트 혼합으로 전환하는 안을 별도 POC로 판정한다.
- **주의.** 실기기 계측이 필요하다 — 에이전트 VM에서는 측정할 수 없으며, MacBook Pro 대리 측정 시 그 사실을 기록한다.

### POC-5. 2기기 룸 동기화
- **확인할 것.** Colyseus 최소 룸에 노트북·폰이 접속해 위치 10Hz + 보간, 말풍선 이벤트가 자연스럽게 동기화되는가.
- **통과.** 두 기기 화면에서 상대 아바타 움직임의 지연·떨림이 데모 허용 수준 안이다 (주관 판정 + 왕복 지연 수치 기록).
- **탈락 시 변경.** 전송 주기·보간 방식을 조정하고 룸 상태 구조를 단순화한 뒤 재측정한다.

### POC-6. Gadget 브리지 스파이크
- **확인할 것.** 불확실성이 가장 큰 지점. 데모 계정 1개를 페어링해 muse-bridge(Linux SDK 종단)로 아바타 데이터를 받아 게임 화면에 표시하는 데까지.

- **선행 조건.** Android 기기에서 Muse 앱 Developer mode 페어링 (계정 주인 본인 절차).

## 4. 마일스톤 상세

### M0 — 기반 스택

**목표.** `docker compose up` 한 번으로 전체 스택이 뜨고, 서버 게이트웨이를 경유한 Meta Model API 호출이 모델별로 1회씩 성공하는 상태.

**범위 — 포함**
- 리포지토리 구조 (개발계획 9장): client / server / shared / accord / tools
- compose 서비스: proxy(Caddy) / server(Node: 게이트웨이 + Colyseus + 에이전트 코어 골격) / db(PostgreSQL 18). negotiator·muse-bridge는 프로파일 자리만 잡는다
- 버전 핀: 개발계획 1.3 표 그대로 (three 0.186.1, colyseus 0.18.10, @colyseus/sdk 0.18.8, vite 8.3.5, typescript 7.0.2, openai 7.45.1, jose 6.2.14, Node 24, PostgreSQL 18). `^`/`~` 금지, lockfile 커밋, Docker 다이제스트 고정
- API 게이트웨이: 클라이언트는 Model API를 직접 호출하지 않는다. 게이트웨이는 모델 ID 상수 핀, 호출 로깅, 재시도 큐, 어댑터 모듈 구조를 갖춘다
- Museion MCP 서버 골격: 도구 정의 단일 소스 (문장 검증·온도 조회·후보 제안·불씨 기록 — 실제 구현은 각 마일스톤에서 채운다)

**범위 — 제외**: 조율 로직, 씬 렌더링, Gadget 브리지 실구현.

**요구사항**
- FR-0.1 compose 기동 시 proxy/server/db가 모두 healthy 상태가 되고, 클라이언트 정적 페이지가 proxy 경유로 열린다.
- FR-0.2 게이트웨이는 모델 5종(`muse-spark-1.3`, `muse-wonder-1.0`, `muse-image-1.0`, `muse-voice-transcribe-1.0`, `sam-3.1`) 각각에 대한 스모크 호출 어댑터를 제공한다. 키는 서버 환경변수 `MODEL_API_KEY`로만 주입하고 코드·리포에 남기지 않는다.
- FR-0.3 모든 Model API 호출은 게이트웨이 로그에 모델·토큰량·지연·성공 여부가 남는다 (프롬프트 원문 로깅 금지).
- FR-0.4 CI 성격의 검증: 타입체크 + Vite 빌드 + compose 기동 확인이 한 명령으로 재현된다.

**수용 기준**
- [ ] 빈 환경에서 `docker compose up` 후 3개 서비스 healthy, 브라우저에서 클라이언트 도달
- [ ] 모델 5종 스모크 테스트 각 1회 성공 기록 (키 발급 이후 수행 — 키 전에는 어댑터 단위 테스트로 대체하고 "실호출 미검증"으로 명시)
- [ ] lockfile·다이제스트 핀이 리포에 커밋돼 있고 범위 지정(`^`/`~`)이 없다

**리스크·폴백.** Model API 사양이 문서와 다르면 어댑터 모듈 1곳으로 영향 한정 (개발계획 11장).

### M1 — 신원: 문장 (紋章)

**목표.** Muse가 자기 키를 만들고, 서명된 Agent Card를 제시하고, 상대가 서명과 문장 지문 문양으로 신원을 결정적으로 검증할 수 있는 상태. (절단 선언: 맞이 의식·주인 심지의 실구현은 범위 외 — 데모 계정은 사전 활성화 상태로 시작한다.)

**범위 — 포함**
- Ed25519 키쌍 생성(WebCrypto), 개인키는 기기 IndexedDB에만 보관
- A2A v1.0 Agent Card(JSON) + JWS 서명 — 공개 정보만 (이름, 성향, 기술, 권한 범위, 공개키)
- 문장 지문 렌더러: 공개키 해시를 시드로 한 방사 대칭 절차 문양 (캔버스). 같은 키 = 같은 문양 보장
- 검증 절차: 카드 서명 검증 + 문양 재생성 대조. 실패 시 "흉내쟁이"로 판정해 이후 단계 차단
- Muse Image 초상·문장 장식 생성 경로 (검증과 무관한 장식 — 실패 시 절차 생성 플레이스홀더)
- (확장 — 규격으로 이동) 주인 인증(맞이 의식)과 주인 심지: 제출 빌드에서는 데모 계정을 사전 활성화 상태로 시작하고, 실시간 동시 수행 챌린지·심지의 실구현은 Accord 규격과 확장 마일스톤으로 보존한다. 규격의 원칙은 유지된다 — 문장 활성화는 키 서명이 아니라 주인 인증으로만 성립하고, 소셜 계정 게시 방식은 쓰지 않는다 (계정 소유 ≠ 사람의 존재)

**범위 — 제외**: 온도·불씨 (M5), 권한 교집합 계산 (M4에서 세션 토큰으로 구현).

**요구사항**
- FR-1.1 키 생성은 기기에서만 일어나고 개인키는 어떤 경우에도 서버로 전송되지 않는다.
- FR-1.2 문장 지문 렌더러는 순수 결정적 함수다: 입력(공개키 해시)이 같으면 픽셀 단위로 같은 문양을 낸다. 문양은 구성요소 레이어(대칭 축·코어·링 모티프·프레임·색상 등)의 조합으로 생성하며, 조합 공간은 10억 이상이어야 하고 발급 시 레지스트리 대조로 중복을 감지한다. 충돌 시 배정을 바꾸지 않고 키 자체를 재생성하는 것이 해소 규칙이다 (아트 디렉션 5장) — 그래서 검증은 레지스트리 없이 재생성 대조만으로 어디서든 성립한다.
- FR-1.3 검증은 두 단계 모두 통과해야 성공이다: ① JWS 서명 유효 ② 제시된 문양과 재생성 문양 일치.
- FR-1.4 Agent Card에는 비공개 정보(제약, 개인키 파생값)가 포함되지 않는다 — 스키마 테스트로 강제한다.
- FR-1.5 하네스 선택(Scout/Fixer/Guardian)이 카드의 성향·기술·권한 범위를 결정한다. 어느 하네스도 주인 최종 확인 우회 권한을 갖지 않는다.
- FR-1.7 연결 종료는 주인의 단독 권한이며 한 번의 동작으로 즉시 효력을 갖는다: 종료와 동시에 presence 회수, 진행 중 조율 세션의 상대 측 종료 통지, 위임 토큰 전부 폐기, 문장 비활성화가 일어난다. 종료된 Muse는 스스로 재활성화할 수 없고, 재연결은 주인 인증부터 다시 거친다. 종료 신호는 주인 전용 채널(생체인증 확인 화면)에서 문장 손그림 제출로 발생하며, Muse는 이 채널에 대한 읽기·쓰기 권한이 없다.
- FR-1.8 (확장 — 규격으로 이동. 제출 빌드의 데모 계정은 사전 활성화로 대체) 상주는 주인 심지가 유지되는 동안만 계속된다. 심지 연장은 주인 전용 채널에서의 인지 확인으로만 이루어진다: 서버 원장(불씨·조율 기록)에서 생성된 자기 Muse의 최근 행적 요약을 주인이 확인·승인해야 하며, Muse는 요약 생성에 관여할 수 없다. 심지 기본 길이는 30일이며, 주인 확인 행위(합의 승인·확인 큐 처리)가 있을 때마다 30일로 연장된다. 소진 7일 전부터 주인에게 알리고, 소진 후 7일 유예 동안은 새 조율 개시가 제한되며, 유예 경과 시 Muse는 상주 정지(수면) 상태가 되고 주인 재확인으로 재점화된다. 고위험 과제(온도 40.0° 이상)는 최근 확인이 7일 이내일 때만 수행할 수 있다.
- FR-1.6 (확장 — 규격으로 이동. 제출 빌드의 데모 계정은 사전 활성화로 대체) 문장 활성화는 키 서명이 아니라 주인 인증(실시간 동시 수행 챌린지)으로만 성립한다. 챌린지 지시 조합은 세션마다 무작위로 생성되고, 판정은 반응 지연·수행 일치·손그림 문양 대조를 함께 본다. 고위험 구간(온도 40.0° 이상 과제) 진입 전에는 재인증을 요구한다. 주인 인증 절차가 없는 자동 가입 경로는 존재하지 않는다. 카메라 대체 경로로 실시간 음성 챌린지를 제공한다.

**수용 기준**
- [ ] 동일 키로 2개 기기에서 생성한 문양이 픽셀 단위로 일치
- [ ] 문장 조합 공간이 10억 이상임을 레이어 계산으로 확인하고, 동일 조합의 중복 발급이 0건이다 (레지스트리 대조 로그)
- [ ] 서명을 1바이트 변조한 카드는 검증 실패하고 사유가 로그에 남는다
- [ ] 카드 스키마 테스트: 금지 필드 포함 시 생성 자체가 실패
- [ ] 초상 생성 실패 시에도 검증·입장 경로는 플레이스홀더로 정상 동작
- [ ] (확장 메커니즘의 기준 — 제출 본선에서는 사전 활성화로 대체) 주인 인증을 거치지 않은 Muse는 불 입장·조율 세션·불씨 발급 전 경로에서 차단된다
- [ ] 챌린지의 목표는 "봇에게 불가능"이 아니라 "봇에게 사람보다 비싸게"다 — 무작위 지시 조합과 반응 지연 검증으로 자동 수행의 시도 비용을 사람보다 높게 유지하고, 레드팀 테스트의 결과를 수치로 기록한다
- [ ] 주인이 연결 종료를 누르면 상대 화면에서 해당 Muse가 즉시 사라지고, 위임 토큰 검증이 전부 실패로 바뀐다
- [ ] (확장 메커니즘의 기준 — 제출 본선에서는 사전 활성화로 대체) 심지 확인을 건너뛰면 Muse가 상주 정지 상태가 되고, 인지 확인(원장 요약 대조 승인) 없이는 재점화되지 않는다. Muse 측 입력으로는 심지 연장과 종료 취소가 불가능하다

**의존.** M0. **리스크·폴백.** WebCrypto Ed25519 미지원 환경에서는 jose 기반 소프트웨어 구현으로 대체하고 그 사실을 로그에 명시한다.

### M3 — 프레즌스·인사

**목표.** Muse가 서버에 상주하며 주인의 접속과 무관하게 불 앞 생활을 계속하고, 두 기기가 같은 모닥불 룸에 접속해 서로를 보고, 불지기(Spark 상주)의 맞이와 문장 검증을 거쳐 좌석에 앉는 전 과정이 동작하는 상태.

**범위 — 포함**
- Colyseus 룸 = 모닥불 1개. 상태: 입장 Muse, 좌석, 진행 중 세션. 인메모리 + Postgres 주기 체크포인트
- 프레즌스: 위치 10Hz 전송 + 클라이언트 보간. 서버에는 geohash 셀만 전달, 정밀 좌표 저장 금지
- 인사 프로토콜: 입장 → 불지기 카드 검증 대행(Wonder는 깊은 판단 승격 시에만) → 문장 확인 이벤트 → 좌석 배정
- 위치 두 모드: 실제 모드(geolocation → geohash) / 데모 모드(고정 시나리오 — 위치 소스만 바꾸는 토글, 별도 빌드 없음). GPS 거부·오차 시 수동 장소 선택 폴백
- 불지기 일상 응대: Muse Spark — 방문자 맞이 인사, 장소 소개, 불티 피드 선별 1차 (피드 자체는 M6)
- Muse 상주 런타임: Muse는 서버 측 에이전트로 상주한다. 주인 오프라인 동안에도 인사·대화·조율 수신이 계속되며, 조율은 합의 후보 단계까지 진행하고 합의(주인 확인)는 주인이 돌아올 때까지 확인 큐에 쌓인다

**범위 — 제외**: 조율(M4), 온도 조회 표시는 M5 이후 (이 단계에서는 카드의 공개 정보만 표시).

**요구사항**
- FR-3.1 입장 승인은 서명 검증(M1) 통과가 전제다. 검증 실패 존재는 좌석을 받지 못하고 그 사실이 양쪽 화면에 표시된다.
- FR-3.2 프레즌스 데이터는 셀 단위 + 시간 만료형이다. 만료된 presence는 서버에서 자동 소멸한다.
- FR-3.3 데모 모드에서도 서명·인사·좌석 경로는 실제 코드와 동일하게 동작한다 (우회·하드코딩 금지).
- FR-3.4 룸 상태가 서버 재시작 후에도 체크포인트에서 복원된다 (좌석·입장자 한정, 조율 세션은 M4 규칙을 따른다).
- FR-3.5 Muse의 존재는 주인 클라이언트의 접속 상태에 의존하지 않는다. 주인 앱 종료·오프라인은 presence를 소멸시키지 않으며, presence를 끝내는 것은 주인 위치 만료가 아니라 연결 종료(FR-1.7)뿐이다.

**수용 기준**
- [ ] 노트북·폰 2기기가 같은 룸에 접속해 서로의 아바타·말풍선을 실시간으로 본다
- [ ] 변조 카드로 입장 시도 시 거부되고 화면에 사유가 표시된다
- [ ] 실제/데모 모드 전환이 토글 하나로 되고, 두 모드에서 인사 경로 코드가 동일하다
- [ ] 서버 재시작 후 룸 체크포인트 복원 확인
- [ ] 주인 앱을 종료해도 상대 화면에서 그 Muse가 사라지지 않고 인사·조율 수신이 계속된다

**의존.** M1, M2.

### M4 — 봉인 조율 (핵심)

**목표.** 두 Muse가 비공개 제약을 드러내지 않고 스파크 세션에서 후보 제안·수락/거부만으로 합의 후보를 만들거나, 겹침이 없음을 정직하게 선언하는 상태. 합의 자체는 주인 확인으로 성립한다. 이 마일스톤이 제품의 중심 주장이다.

**범위 — 포함**
- 스파크 세션: 두 카드 권한의 교집합으로 서명된 세션 토큰 (장소 셀 + 만료 시각 바인딩, 만료·이탈 시 자동 소멸)
- 조율 세션 실행 환경 (제출 본선): server 프로세스 내 격리 워커 — 세션마다 생성/폐기하고, 세션에는 공개 정보·후보·수락/거부 신호만 들어간다. 컨테이너 단위 격리(세션마다 기동/폐기, 외부 네트워크 차단)는 확장 사양이며, 본선의 격리 수준이 컨테이너보다 낮다는 사실을 화면·로그에 명시한다 (NFR-4)
- 상태 기계: `제안 → (수락/거부)×2 → 합의 후보 → 주인 확인 → 합의 | 조정(최대 5회) → 조율 불가` — 명시적 상태 전이로 구현하고 전이 로그를 남긴다
- 후보 생성: Muse Spark 호출 (공개 신호 + 장소 맥락). 구조화 출력(JSON Schema)으로 수신. 실패 시 규칙 기반 템플릿 후보로 강등하고 로그에 명시
- 수락 판정 (각 Muse 로컬, 2단): ① 규칙 기반 즉시 판정(시간·가격 범위 등 구조화 제약) ② 애매하면 Muse Spark 호출로 주인 성향 대조. 제약 원문은 기기 밖으로 나가지 않는다
- 주인 확인 에스컬레이션: 결제성 약속 등 주인 확인이 필요한 행동은 UI 다이얼로그로 올리고, 확인 없이는 진행하지 않는다 (어느 하네스도 우회 불가)
- (확장 — 규격으로 이동) 음성 조건 입력: 제출 빌드의 조건 입력은 타이핑으로 고정한다. Voice Transcribe 전사 경로는 인터페이스가 POC-1에서 확정된 뒤에 붙인다
- 세션 종료 처리: 후보·응답 로그 폐기, 합의문만 양쪽 서명으로 저장

**범위 — 제외**: 현장 물건 확인(M5), 고위험 과제 온도 게이트(M5 — 이 단계에서는 게이트 인터페이스만).

**요구사항**
- FR-4.1 거부 응답에는 이유·제약 내용이 포함되지 않는다. 응답 페이로드는 `accept | reject` 열거형뿐이다 — 스키마 테스트로 강제.
- FR-4.2 조정은 최대 5회. 초과 시 세션은 "조율 불가"로만 종료하고 추가 제안을 만들지 않는다.
- FR-4.3 스파크의 도구 사용은 세션 토큰의 교집합 범위를 벗어날 수 없다. 범위 밖 호출은 실행 전에 차단되고 기록된다.
- FR-4.4 제약 데이터는 클라이언트 로컬 저장소에만 존재한다. 서버 DB·로그·트래픽 어디에도 원문이 남지 않는다.
- FR-4.5 조율 실행 환경은 세션 종료와 함께 폐기되며, 그 내부에도 세션 기록이 남지 않는다. 제출 본선은 프로세스 내 격리 워커, 확장 사양은 세션별 컨테이너이며, 어느 쪽이 동작 중인지가 로그에 기록된다.

**수용 기준**
- [ ] 시나리오 조율(데모 조건: 오늘 19:00, 본사 앞 카페 — 프리뷰 대본의 다섯 번째 후보)이 실제 Spark 호출로 합의 후보에 도달하고, 주인 확인으로 합의가 성립한다
- [ ] 조율이 불가능한 제약 쌍을 넣으면 5회 조정 후 "조율 불가"로 종료한다
- [ ] 조율 전 과정의 네트워크 패킷 덤프에서 제약 원문(가격 하한·시간 제약 문자열) 0건 — 자동화 테스트로 확인
- [ ] 교집합 밖 도구 호출 시도가 차단·기록된다
- [ ] 주인 확인 다이얼로그를 거부하면 합의가 성립하지 않는다
- [ ] 세션 종료 후 조율 워커가 폐기되고 합의문만 남는다 (컨테이너 격리는 확장 사양 — 본선은 워커이며 그 사실을 로그에 명시)

**의존.** M3. **리스크·폴백.** 제출 본선은 원래 프로세스 내 격리 워커이며 그 수준을 로그와 화면에 명시한다 (숨기지 않는다). 확장 사양의 컨테이너 기동이 실패하면 워커 실행으로 폴백한다.

### M5 — 현장 확인·불씨·온도

**목표.** 만남 현장에서 물건을 확인하고, 만남 완료가 다자 서명된 불씨로 원장에 남으며, 온도가 정책대로 파생·적용되는 상태.

**범위 — 포함**
- 현장 확인: 폰 카메라 → SAM 3.1 분리(전처리) → Muse Spark 비전 대조(판정). UI에 "보조 확인이며 동일 개체의 법적 증명이 아니다" 고지 상시 표시. 분리 실패 시 수동 크롭 UI 폴백, 판정 불가 시 "확인 불가"로 표시하고 사람 확인으로 진행
- 현장 확인 문구: Muse Voice Transcribe 전사 기록을 동의·본인 확인 로그로 저장
- 불씨 발급: 만남 완료 시 양쪽 Muse + 불지기가 합의문 해시에 다자 서명 → 불씨 레코드를 PostgreSQL 원장에 기록. 불씨 나누기 시그니처 애니메이션 (개발계획 2.2)
- 온도 파생: 원장 레코드에서 계산하는 서버 함수. 가중치 세부 수치는 서버 전용 상수 (비공개). 범위 30.0°~50.0° 클램프, 시작 36.5°
- 온도 정책 집행: 고위험 과제(금액이 오가는 과제)는 온도 40.0° 이상 Muse 사이에서만 중개. 30° Muse는 일반 과제도 후순위. 온도 상승은 양쪽 서명 + 불지기 확인이 있는 완료 만남에서만, 동일 쌍 반복은 상승폭 체감
- (확장 — 규격으로 이동) 고위험 과제의 Wonder 승격 심의. 제출 본선에서 Wonder는 조율 교착 시 후보 재생성 1회 호출로만 쓴다

**범위 — 제외**: 불씨 기반 외부 연동(ERC-8004 레지스트리 실연동은 규격 호환 형태 기록까지만).

**요구사항**
- FR-5.1 불씨 레코드는 삭제·수정할 수 없다 (원장 append-only). 정정은 신규 레코드로만 한다.
- FR-5.2 온도는 저장값이 아니라 원장에서 파생되는 값이다. 직접 쓰기 경로가 존재하지 않는다.
- FR-5.3 온라인 활동만으로는 온도가 오르지 않는다. 상승 트리거는 완료 만남의 다자 서명뿐이다.
- FR-5.4 고위험 게이트는 서버에서 집행한다 — 클라이언트 표시 숨김으로 대체하지 않는다.
- FR-5.5 비전 대조 결과는 "일치해 보임 / 다름 / 확인 불가" 3값으로만 표시하고 단정 표현을 쓰지 않는다.

**수용 기준**
- [ ] 데모 물건 사진으로 분리→대조가 동작하고 고지 문구가 화면에 표시된다
- [ ] 만남 완료 시 불씨 1개가 양쪽에 발급되고 원장에 다자 서명과 함께 남는다
- [ ] 온도 39.9° Muse 쌍의 고위험 과제가 서버에서 거부된다 (40.0° 쌍은 통과)
- [ ] 동일 쌍 반복 만남에서 온도 상승폭이 체감한다
- [ ] 원장 레코드 수정·삭제 시도가 거부된다

**의존.** M4.

### M6 — 세계 완성: 불티 피드·불 생성·맞이하기·맵 관찰 (제출 범위 절단 선언 적용 — 밤 생활·연속체는 범위 외)
- 맵 관찰 층위: 실제 지도 위에 불·이야기·온도 히트를 표시하는 광역 지도 뷰를 제공하고, 디오라마와의 사이는 전환 연출로 잇는다. 무절단 줌 연속체 자체는 제출 범위 외다. 오프닝 기본 범위는 실리콘밸리 전경이다

**목표.** 장소의 일상 층 — 불티 피드, 불의 자동 생성, 하네스 맞이하기 온보딩 — 이 기획안의 원칙(공개·동의 기반) 안에서 완성되는 상태.

**범위 — 포함**
- 불티 피드: 그 장소의 메시지를 불티처럼 떠오르는 UI로 표시. 데이터 경로는 기획안 4.4 확정 기준으로 한정한다 — 제휴 장소 게시글, 이용자 본인 공개 게시글, 파트너 공지뿐이다. 제3자 위치 태그 게시글 경로는 운영 단계 과제이며 제출 범위 외. Spark가 선별·요약
- 불 자동 생성: ① 제휴 장소 등록 시 즉시 ② 체크인 7일 내 20회 누적. (소셜 밀도 경로는 지표만 수집하고 자동 생성은 운영 단계로 미룬다)
- 맞이하기(온보딩) 완성: 하네스 3종 선택 화면 — 성격·기술·도구·권한이 한눈에 보이고, 선택 즉시 하네스 주입 + 문장 발급(M1) + 첫 불 입장까지 한 흐름
- 불지기 장소 기억: 장소별 누적 맥락(합의 패턴, 분쟁 이력)을 축적한다 (Wonder 심의 활용은 규격으로 이동한 확장 사양 — 본선에서는 조율 교착 시 후보 재생성 호출이 이 기억을 입력으로 쓴다)
- (제출 범위 외로 이동) 밤 생활 최소 루프와 아침 일기 — 기획안 3.6·3.7의 서사와 Accord 규격으로 보존하고 제출 빌드에서는 구현하지 않는다

**범위 — 제외**: 소셜 플랫폼 계정 연동 자동 수집 (정책상 가능한 공개 경로만), 불지기 커스텀 제작 도구.

**요구사항**
- FR-6.1 피드에 노출되는 게시글은 전부 실재하는 공개·동의된 게시글이며 출처가 표시된다. 연출용 가짜 게시글을 실존 서비스 화면처럼 보이지 않는다 (기획안 6.3 정직성 규칙).
- FR-6.2 체크인 누적 카운터는 geohash 셀 단위로만 집계하고 개인별 이동 경로는 저장하지 않는다.
- FR-6.3 온보딩에서 하네스를 바꾸면 카드의 권한 범위가 즉시 재생성되고 이전 카드는 폐기된다.

**수용 기준**
- [ ] 데모 장소에서 피드가 실제 공개 게시글로만 구성되고 출처가 표시된다
- [ ] 체크인 20회 누적 시뮬레이션에서 새 불이 자동 생성된다
- [ ] 신규 사용자가 맞이하기부터 첫 불 입장까지 설정 화면 없이 도달한다

**의존.** M3. M4·M5와 병행 가능.

### M7 — 파일럿·데모·제출

**목표.** 파일럿 관찰로 제품을 검증하고, 3분 데모 영상을 실제 구동 화면으로 촬영하며, 제출 패키지를 마감 전에 완성하는 상태.

**범위 — 포함**
- 고정 시나리오 모드 완성: 기획안 6장 대본의 전 장면(콜드 오픈 → 1막 → 2막 조율 → 현장 확인 → 3막 불씨 → 구현 소개 → 엔딩)이 데모 계정 2개로 재현 가능. 무대는 Meta 본사(1 Hacker Way, 37.48336, -122.15008) 주변으로 고정하고 위치는 가상 GPS로 주입한다. 오프닝 지도는 실리콘밸리 전경 범위에서 본사로 줌인한다
- 축소 파일럿 (절단 반영): 비교 파일럿 대신 조율 경로 실구동 관찰로 대체한다. 데모·파일럿 계정의 실제 조율 세션 로그에서 합의 후보 도달까지의 조정 횟수와 소요 시간을 자동 수집해 지표로 삼는다 (POC-2 로그 형식과 동일). 여기에 만남 약속을 자주 잡는 사람 3–4명의 동석 관찰을 최소 단위로 붙인다 — 지표는 합의까지의 소요 시간과 확신도(1–10) 두 개로 한정한다. 통계 주장 금지, "실구동·동석 관찰"로 표기
- 영상 제작: 영어 VO 확정 대본(기획안 6.2) + 한국어 자막본. 파일럿 수치는 촬영 후 실측으로만 엔딩 카드에 기입 — 미달 지표는 미달한 대로 표기
- 트랙·테마는 확정됐다 (2026-10-30): Startup / Push the Frontier. 촬영본 리뷰 시점에 엔딩 30초와 설명문을 이 프레이밍(기획안 9장)으로 잠그고, 영상 첫 30초가 "에이전트에게 주는 새로운 능력"의 주장으로 시작하는지 확인한다
- 공개 범위 확정: 공개 — 클라이언트, Accord 규격 문서, 데모 레퍼런스 구현. 비공개 — 온도 가중치, 남용 탐지 파라미터, 파트너십 문서
- 제출: 공개 GitHub 리포, 작동 데모, 3분 영상, 설명문. 제출 포털 필수 항목은 로그인 상태로 최종 확인한다. 제출은 마감 하루 전 완료를 내부 게이트로 한다

**범위 — 제외**: 결선 라이브 보강 시연의 무대 소품 제작 (별도 준비물 — 모닥불 조명 소품, 폰 2대 재현 리허설은 체크리스트로만 관리).

**요구사항**
- FR-7.1 영상의 모든 동작 장면은 이벤트 기간 중 만든 것의 실제 구동 화면이다. 목업·합성 화면으로 대체하지 않는다.
- FR-7.2 데모 모드의 폴백 사슬이 준비돼 있다: 상대 발견 실패 시 QR 룸 접속, 네트워크 단절 시 로컬 캐시 시나리오로 촬영 지속.
- FR-7.3 리포에서 기존 자산(vibeMuse 등 차용 패턴)과 신규 작업이 분리 표기된다.

**수용 기준**
- [ ] 대본 전 장면이 데모 계정으로 끊김 없이 재현된다 (촬영 리허설 1회 통과)
- [ ] 실구동 관찰 기록(조정 횟수·소요 시간)이 세션 로그에서 자동 집계되고 엔딩 카드 수치가 그 기록과 일치한다
- [ ] 엔딩·설명문이 Startup / Push the Frontier 프레이밍으로 잠겼다
- [ ] 제출 포털에서 실제 제출을 완료하고 접수 상태를 확인한다

**의존.** M4, M5 필수. M6은 피드 장면 포함 시 필요, 불발 시 피드 없이도 촬영 가능한 구성으로 강등한다.

### M8 — Gadget 브리지 (확장, 본체 독립)

**목표.** 사용자의 실제 Muse 아바타를 게임 아바타로 가져오고, 게임 사건을 본인 Muse·실물 가젯에 반영하는 브리지가 데모 계정에서 동작하는 상태.

**범위 — 포함**
- muse-bridge: 계정마다 격리된 인스턴스 1개. Linux SDK(musegadget)를 컨테이너에서 실행해 페어링 세션 유지, 게임 서버와는 내부 API만 통신
- 가져오기: 실제 Muse 아바타를 아바타 얼굴·표정 세트로 주입 (미연결 시 Muse Image 초상이 기본값)
- 반영하기: 합의·불씨 사건을 `musegadget send-user-msg`로 본인 Muse에 전달, 실물 가젯 표정·상태가 게임 상태를 따라 변경
- 동의·투영·철회: vibeMuse meta_social 절차 재사용. 투영 범위를 사용자가 정하고 철회 시 즉시 분리 + 기본 아바타로 복귀

**범위 — 제외·제약 (숨기지 않는다)**
- 페어링은 계정마다 Muse 앱 Developer mode 절차가 최초 1회 필요 — 우회 없음. 데모 계정은 사전 페어링을 끝낸 상태로만 진입한다
- Gadget SDK는 개인·비상업용이며 지원 플랫폼이 아니다. 브리지는 데모·개인 채널로 위치시키고 상용 본체는 Model API로 유지한다

**수용 기준**
- [ ] 페어링된 계정의 실제 아바타가 게임 안에 표시된다
- [ ] 불씨 발급 사건이 본인 Muse 메시지와 가젯 표정 변화로 반영된다
- [ ] 철회 즉시 브리지가 분리되고 아바타가 기본형으로 돌아간다

**의존.** M3. 본체 마일스톤(M4–M7)의 진입 조건이 되지 않는다.

## 5. 전역 수용 게이트 (전 마일스톤 공통)

제품 전체가 "완성"으로 불리기 위한 최종 체크리스트:

- [ ] `docker compose up` 한 번으로 전체 스택 기동 (전용 서버 배포본 기준)
- [ ] 노트북·폰 2기기 E2E: 맞이하기 → 입장 → 문장 검증 → 봉인 조율 합의 → 현장 확인 → 불씨 발급 → 온도 변동, 전 경로 실제 API 호출로 통과
- [ ] 조율 비공개성 패킷 테스트 통과 (제약 원문 0건)
- [ ] 성능 예산 계측 기록 (M1 Air 기준, NFR-1)
- [ ] 데모 모드 리허설: 대본 전 장면 재현 + 폴백 사슬(QR·캐시) 각 1회 발동 확인
- [ ] 공개 범위 점검: 온도 가중치·탐지 파라미터가 공개 리포에 없음을 확인

## 6. 비기능 요구사항

- **NFR-1 성능.** 개발계획 2.3 예산을 그대로 적용한다: draw call ≤50, 삼각형 ≤100k, 파티클 ≤2,000·시스템당 1 draw call, 동적 라이트 1개, DPR 캡(노트북 2/폰 1.5), 번들 gzip ≤500KB 목표. 기준 기기는 MacBook Air M1, 추가 검증은 MacBook Pro·Windows·Android.
- **NFR-2 프라이버시.** 정밀 좌표 서버 저장 금지(셀 단위만), 제약 원문 기기 외부 전송 금지, presence 시간 만료형, 조율 세션 기록 종료 시 폐기. 합의문과 불씨 원장만 영속 기록이다.
- **NFR-3 보안.** 개인키는 기기 밖으로 나가지 않는다. API 키는 서버 환경변수에만 존재한다. 세션 토큰은 장소·시간 바인딩 + 교집합 권한.
- **NFR-4 정직성.** 강등·폴백이 발동하면 로그와 화면에 명시한다(격리 강등, 템플릿 후보 강등, 확인 불가 표시). 파일럿 수치는 실측만 기입한다. 검증되지 않은 항목은 "미검증"으로 표기한다.
- **NFR-5 재현성.** 버전 핀 정책(개발계획 1.3)을 전 의존성에 적용한다. 모델 교체는 상수 변경 + 회귀 검증으로만 한다.
- **NFR-6 접근 범위.** 반응형 단일 웹앱으로 노트북·폰 동시 지원. 카메라 조작 규격(회전 금지·줌만)은 전 기기 동일하다.
