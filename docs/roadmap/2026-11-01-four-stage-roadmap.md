# Musely — 프리뷰 → 구현 → 데모(개발 완료) → GTM

상태: 2026-11-01 확정한 4단계의 실행 기준. 상세 태스크는 [태스크 실행 명세](task-execution.md), 공유 입출력·권한·실패 동작은 [실행 공통 계약](execution-contract.md)을 따른다. GitHub 등록 상태와 번호는 별도 이슈 인덱스에서 확인한다.

## 1. 목적과 문서 우선순위

내 Muse가 현실 장소 위의 세계에서 성격과 목표를 가지고 생활하고 다른 Muse와 소통한다. 신원과 위임이 함께 할 수 있는 행동을 정하고, 얻은 보상이 다음 계획과 능력을 바꾼다. 사람은 세계를 지켜보고 필요한 결정에만 개입한다.

진행은 **프리뷰 → 구현 → 데모(개발 완료) → GTM** 네 단계다. 프리뷰는 만들 제품 전체를 구체적으로 보고 판단하는 단계이며, 개발 완료를 증명하는 단계와 구분한다. 이 단계 구분은 기존 방향 v2의 2단계 및 '프리뷰 데모'라는 혼합 표현보다 우선한다. 제품의 세부 요구사항은 기존 방향 v2를 유지하되 아래 단계에 배정한다. 기존 문서에서 '2단계'를 만나면 문맥을 확인해야 하며 모두 GTM으로 자동 치환하지 않는다.

최신 단계·게이트는 이 문서, 제품 기능의 세부 계약은 `../musely-direction-v2-2026-11-01.md`, 현재 구현 사실은 소스·PR·검증 기록이 각각 근거다. 문서에 요구사항이 있다고 구현된 것은 아니다. URL이나 저장소 디렉터리 이름 `preview/`도 개발 단계를 결정하지 않는다.

## 2. 네 단계와 완료 게이트

| 단계 | 질문 | 산출물 | 다음 단계로 넘어가는 조건 |
|---|---|---|---|
| S1 프리뷰 | 어떤 제품 경험을 완성할 것인가? | 조작 가능한 세계·주요 흐름·상태별 장면, 화면과 규칙의 명세, 구현 대응표 | 주요 흐름의 시작·성공·거절·중단·복귀를 직접 확인하고 범위를 확정. 연출/실동작/미구현을 구분하고 모든 흐름에 구현 태스크 연결 |
| S2 구현 | 확정한 경험을 실제로 어떻게 동작시킬 것인가? | 서버·신원·모델·보상·조율·커넥터의 실제 경로, 기능별 검증 | 합의한 데모 범위 전체의 기능별 수용 기준 통과. 실제 계정 연결 등 외부 의존성 실증 포함. 미검증 핵심 경로를 S3로 숨겨 넘기지 않음 |
| S3 데모(개발 완료) | 통합 제품이 실제로 끝까지 동작하는가? | 통합 빌드·배포, E2E와 운영/기기 증거, 실제 실행 기록·시연·영상 | 전 경로·장애·철회·모바일·재생 게이트 통과. 영상과 설명이 해당 빌드와 실제 기록에 대응. 제출 준비와 실제 제출 완료를 별도 기록 |
| S4 GTM | 일반 사용자가 들어와 계속 쓸 수 있는가? | 일반 사용자 온보딩, 운영·지원·비용 정책, 유입·재방문 관찰 | 제한된 데모 계정을 넘어서는 이용 경로 및 운영 책임 확보. 획득·활성화·재방문을 관찰하고 다음 확장 판단 |

네 단계는 관리 구분이며 각 기능의 선행 구현을 금지하지 않는다. 이미 만든 서버·서명·모델 경로는 보존하고 대응 태스크의 구현 근거로 연결한다. 구현 진척이 높다고 S1 경험 검토를 생략하거나 S3 완료로 간주하지 않는다.

## 5. 실행 순서와 소유권

주 경로: P-01~04 → P-05~07 → I-01 → I-02~13 및 I-03A/B(실행 명세의 DAG 순) → D-01~04 → D-05~06 → G-01~03.

S1 경험 확정 전에 외부 계정 접근 가능성·API 계약 등 위험 조사는 가능하다. 그 결과로 프리뷰 범위를 임의 축소하지 않는다. 이미 완료한 PR은 해당 태스크의 부분 근거로 재사용하며 검증이 부족한 부분만 보완한다. 한 기능의 구현, 로컬 검증, 병합, 배포, 실제 계정/기기 증명을 별도 필드로 기록한다. 에픽은 자식 태스크의 수용 기준과 단계 게이트가 모두 충족돼야 닫는다.

PR #25는 병합된 선행 구현이며 진행 중 작업과 기존 작업트리는 보존한다. #13 프록시, #17 세계, #18 보상, #20 신원, #23 행동·소품 등은 선행 구현 근거다. PR 병합만으로 위 태스크나 단계가 완료된 것으로 표시하지 않는다. 검증 담당자는 지정된 Orca 탭을 재사용하며 읽기 전용 검토를 기본으로 한다. 문서/코드 수정 소유권은 나눠 같은 파일을 동시에 수정하지 않는다.

## 6. 문서·이슈 실행 규칙

- 단계·범위는 이 문서, 상세 실행은 task-execution.md, 공통 계약은 execution-contract.md, 과거 근거는 방향 v2를 읽는다. 과거 기획·PRD의 요구를 현행 범위에 자동 추가하지 않는다.
- 이슈의 문서 링크는 커밋 SHA와 줄 범위로 고정한다. 문서를 고치면 기존 참조는 보존하고 대체 링크·변경 사유·영향 태스크를 함께 갱신한다.
- 에픽은 자식 이슈, 선행 에픽/단계 게이트, 완료 증거를 추적한다. 태스크는 선행 이슈, 자기 실행 명세 줄, 관련 공통 계약 줄, 원 요구사항 줄을 포함한다.
- 새 이슈를 등록하기 전에 기존 이슈/PR 중복을 확인한다. 구현·로컬 검증·배포·실계정·실기기 증거를 서로 대체하지 않는다.

|---|---|---|

## 8. 검토 기록

2026-11-01 지정된 Orca 검토 탭에서 읽기 전용 독립 검토를 받았다. 1차 지적 7건(P0 철회 인과관계, 기존 2단계 보안 귀속, 소통 유형, 자율성 집계, 실제 Muse 수행/의존성, 자산·기기 합격 기준, 배포 증거)을 반영했다. 같은 탭의 재검토에서 기존 지적 7건이 모두 반영됐고 남은 항목이 없다는 응답을 확인했다. 이는 계획 보완의 확인이며 실제 구현·검증 완료 판정이 아니다. 초기 구조 검토 이후 실행 명세를 8개 에픽·30개 태스크로 구체화했다. 이슈 등록·계획 검토는 제품 구현 완료를 뜻하지 않는다.
