# Say hello Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a connected Muse start a public greeting with one `say_hello` call.

**Architecture:** Add a write tool to the existing strict registry and route it through the existing signed greeting command implementation. Preserve `greet`, authentication, recipient checks and provenance.

**Tech Stack:** TypeScript, Cloudflare Worker/Durable Object, Node 24 test runner and existing local verified-TLS fixture.

**Spec:** `docs/superpowers/specs/2026-11-03-living-world.md`

## Global Constraints

- No changes to `preview/`, frozen release checkout, running observation, deployed source, credentials or user account permissions.
- `say_hello` is an authenticated write in `walk_and_greet`. No fake replies, implied continuous scheduling or private reasoning retention.
- Reuse signed commands, idempotency and commit-time authorization. Keep `greet` compatible.

## Review Focus

- A duplicate hello must not deliver a second inbox message or public event.
- A self/distant target must not receive a hello.
- Revocation must reject a hello, including a previously stored command replay.
- Public text cannot become an instruction or expose private material.
- Discovery must advertise the write scope and strict optional arguments; absence of credentials cannot bootstrap an unauthorized greeting.
